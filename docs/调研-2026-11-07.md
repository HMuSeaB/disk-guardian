# 图形化路线调研（2026-11-07）

起因：用户问「能不能像 Dism++ 一样图形化；Dism++ 好久没更新，可以魔改成
我们想要的现代化程序吗；GitHub 上同类多，但这种整合、问题更具体的应该比较少」。

调研按 `github-wheel-research` 的流程做：**不只看 README，下源码核对实现**。

---

## 一、「魔改 Dism++」这条路走不通（并纠正我此前的说法）

此前我说过「Dism++ 开源」——**这个说法不准确**。准确的是：

> 开源的是**规则文件、语言包、插件文档与周边 C++ 基础库**；
> **主程序是闭源二进制分发**。

证据：

| 查的东西 | 结果 |
|---|---|
| `GET api.github.com/repos/Chuyu-Team/Dism++` | **404 Not Found** —— 根本没有这个仓库 |
| `GET api.github.com/orgs/Chuyu-Team/repos?per_page=100` | 24 个仓库里没有主程序源码。`Dism-Multi-language` 是语言与 `Data.xml`，MIT，最近 push 2026-10-09；`DismPlusPlus_PluginDevDoc` size=0；`covscript-bridge` 是插件示例；其余是 VC-LTL / YY-Thunks / CPPHelper / MegaUI 等周边库 |
| `Dism-Multi-language` 首页 | 最后一次源码提交 2019-08-25，README 2024-12-17；**最新稳定版的发布附件就挂在这个仓库的 Releases 上**（单 exe 分发） |
| 本机 `Dism++10.1.1002.1` | 目录里只有 exe / dll / `Config\`，没有 `Data.xml`——规则编译进了 exe / `NCleaner.dll` |

网上 `dism.pro` / `dismmax.cn` / `dismplus.com` 等站点都写「MIT 开源」，
但它们不是官方仓库，且与实测矛盾：宣称 2026-05 发布 `10.1.1002.2`、
新增了「NuGet 包缓存」规则；本机是 `10.1.1002.1`，源码 `Data.xml` 里
**没有** NuGet 规则。这类站点是分发/推广页，不能当授权依据。

**结论**：能改的只有 `Data.xml` 规则与写插件，**不能重编译、不能改 UI、
不能改规则引擎**。而改 `Data.xml` 恰恰补不了我们真正缺的东西
（shader / 包管理器缓存规则、事故取证禁区、回收站弹窗、动作流水）。
所以「魔改」这条路天花板很低，不值得投入。

## 二、GitHub 上同类：多，但「整合型」的判断要打一点折

### 现成轮子（有源码、许可可用、还在维护）

| 项目 | 技术 | Stars / 许可 / 最近 push | 定位 |
|---|---|---|---|
| `darkmatter2048/WindowsCleaner` | TypeScript | 5.0k / **NOASSERTION（无明确许可）** / 2026-11-06 | 中文 C 盘清理，轻量免安装 |
| `YGTQ3/disk-butler` | **Tauri 2 + Rust + React** | 650 / MIT / 2026-11-06 | C 盘管家：磁盘透视、一键清理、启动管理、内存体检 |
| `iUnreallx/Quanta-Cleaner` | C++17 + Qt6/QML | MIT / 2026-10-31 | 分类环 + 9 类清理，明暗主题 |
| `demigodmode/DiskSweeperPro` | PySide6 + Rust CLI | Apache-2.0 / 2026-02-12 | 按 Safe/Moderate/Aggressive 分级 |
| 其余长尾 | Python / PowerShell / C# | 多数 0–20 stars | 通用临时文件清理 |

### 下了 `disk-butler` 源码核对（不是只看 README）

`curl codeload.github.com/.../main` 16.7 MB，解包后逐字检索：

- `cleanup.rs:1-3`：明确写「**白名单制**，前端只能传回条目 id，实际路径由本模块重新解析」——
  和我们「GUI 只传 id」的设计一致。
- `cleanup.rs:127-130`：**用了 `SHEmptyRecycleBinW`** —— 正是 2026-11-07 我们实测
  遇到 `$R02DUPK` / `0x80004005` 会弹模态框卡死的那个 API。
- `cleanup.rs:84-104`：`delete_contents()` 直接 `remove_dir_all` / `remove_file`，
  **永久删除**，不是先移入回收站可撤销。
- `cleanup.rs:476` / `knowledge.rs:880`：有 `NVIDIA\DXCache` 与通用 ShaderCache 规则。
  → 所以「Dism++ 的空白」不等于「整个社区的空白」，这点要如实说。
- `knowledge.rs:125`：把 `MEMORY.DMP` 标成「可手动删除，不影响系统」；
  `cleanup.rs:570` 把 `CrashDumps` 列为清理项。
  → 而我们因为 11/4–11/6 的蓝屏取证，把这两处设成**硬禁区**。
- 全仓 `.rs` 检索 `winevt` / `assembly` / `NativeImages` / `事件日志` / `硬禁区`：
  **0 命中**（只有 WinSxS 的 DISM 清理、pagefile 的保守判定）。
- `DESIGN.md` 有「设计宪法」、色板令牌、安全等级徽章，工程质量不低。

### 对用户判断的修正

> 「GitHub 上比较多，但这种整合、问题更具体，应该比较少」

- **一半对**：通用清理器确实泛滥，长尾项目 stars 多为个位数。
- **但「规则驱动 + 只读报告 + 确认后执行 + 每条说明删了会怎样」并不罕见**，
  `disk-butler` 做得相当完整（还有单测、设计宪法、TreeMap）。
  真正少的是下面这一层。

### 我们真正不一样的地方（差异化，不是自我辩护）

| 差异 | 我们 | 通用工具 |
|---|---|---|
| 禁区来源 | **事故取证结论**：清 `winevt` 毁掉蓝屏证据、清 `assembly` 触发 NGEN 重建反吃 2.5 GiB | 通用「危险项」清单，靠人工分级 |
| 禁区位置 | 硬编码在 Python 里，规则表改不动；还拦「父目录当目标」；启动 18 条自测 fail-fast | 多在配置/规则表里 |
| 删除语义 | 两步：移入回收站（可撤销）→ 单独 `--purge` 永久删，两次令牌 | 多数一步永久删 |
| 回收站实现 | 按 `$I`/`$R` 逐批删、坏项跳过，**不用 `SHEmptyRecycleBinW`** | 普遍直接调该 API |
| 观察期上下文 | 25H2 蓝屏观察期不清 dmp / WinSxS / 还原点；本机专属路径（雷电 vmdk、`dedicateddumpfile.sys`） | 无 |
| 审计 | 每行 flush+fsync 日志 + `actions.jsonl` 动作流水 | 多数只有一份运行日志 |

**结论**：值得自己造，但卖点不是「又一个清理器」，而是
**「把一次真实排障的结论固化成不可绕过的约束，并且能图形化地讲清楚为什么」**。

## 三、技术选型

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| A. 魔改 Dism++ | 现成 UI | **主程序闭源，做不到** | 排除 |
| B. 只改 `Data.xml` | 零开发 | 老 UI / 老引擎，补不了禁区与审计 | 排除 |
| C. **Python 引擎 + 回环 WebUI（当前 v0）** | 单一事实来源（GUI 与 CLI 共用 `execute_rules`）、零第三方依赖、用系统 Edge/Chromium 的 `--app=` 得到无地址栏窗口、迭代快 | 依赖本机托管 Python，不是单 exe | **先做这个验证形态** |
| D. Go 单 exe 内嵌网页（wintuner 模式） | 单文件分发、零第三方依赖、本机已有 `internal/webui` 骨架 | 要把 Python 引擎作为子进程 + JSON 通信，或重写逻辑；体积 +4 MB | 形态确认后再包一层 |
| E. Tauri 2 + Rust（disk-butler 路线） | 2.4 MB 安装包、现代 UI | 全量重写，引入 Node + Rust 工具链；对自用工具不划算 | 不采用 |

### C 方案照搬的安全约束（来自 `go-embedded-webui-desktop`）

- **只监听 `127.0.0.1`**，传非回环地址直接拒绝（不警告后放行）。
- **一次性令牌**：首页走 `?t=`，API 走 `X-DG-Token`，首页也校验，防本地 CSRF / iframe。
- **`--app=<url>`** 才有「像本地程序」的窗口；退回 `rundll32 url.dll,FileProtocolHandler`。
- **不自动退出**：后台标签页会被浏览器冻结，心跳会误判成「没人用」；退出交给界面右上角按钮 `/api/quit`。
- **双击用 `pythonw.exe`**（无控制台），启动异常写 `out/gui_crash.txt`，否则用户只看到「双击没反应」。
- CLI 与 GUI **共用 `guardian.execute_rules`**，不复制第二份删除逻辑；
  前端只传规则 id，后端用刚重建的 plan 复核等级/状态/禁区后才动手。
- 中文文案里的引号一律用「」，避免 JS 字符串被 ASCII 双引号截断。

### 验证方式

agent 起的进程活不过工具调用边界，所以验证必须**在一次调用内**
「起 `--no-open` 服务 → 从 `out/gui_run.json` 取实际端口/令牌 →
打 API + 无头截图 → `POST /api/quit`」。打本机端口一律 `--noproxy '*'`。
**不向用户承诺「已经帮你跑起来了」**，让他自己双击。
